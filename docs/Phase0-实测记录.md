## 3. 🔴 核心发现：cpal 锁死了延迟下界

### 现象

`BufferSize::Fixed(256)` 被完全忽略，设备恒定按 **480 帧（10ms）** 给块。
请求 64 到 512 之间的任何值都不会改变它。

### 延迟拆解（cpal 共享模式）

```
输入回调缓冲          480 帧   10.00 ms
环形缓冲目标水位      720 帧   15.00 ms
输出回调缓冲          480 帧   10.00 ms
────────────────────────────────────────
设备 I/O 小计       1680 帧   35.00 ms   ← 后端锁死
PSOLA 算法延迟       960 帧   20.00 ms
────────────────────────────────────────
理论下界                      55.00 ms
```

**即使 DSP 延迟归零，35ms 仍然超过 30ms 的 No-Go 线。**

### cpal 0.18 —— 已试，无效

升级并完成 API 迁移（`SampleRate` 变成 `u32`、`Device::name()` → `description()`、
`build_*_stream` 收值不收引用、错误类型合并）。实测结果与 0.15 **完全一致**：
仍是 480 帧 / 10ms / 55ms。

查源码确认原因：`host/wasapi/device.rs` 里仍然硬编码 `AUDCLNT_SHAREMODE_SHARED`，
没有独占模式，也没有 IAudioClient3。**这条路从设计上就走不通，不是配置问题。**

> 迁移保留了：0.18 的 `StreamTrait::buffer_size()` 能直接查实际块大小。

## 4. ✅ 出路：WASAPI 独占模式

### 4.1 硬件能力探针

写了 `wasapi-probe` 直接问 Windows 音频 API，**不写整个后端就拿到答案**：

| 设备 | 共享默认 | 独占最小 | IAudioClient3 最小 |
|---|---|---|---|
| 输入：麦克风阵列（Intel 智音） | 10 ms | 2 ms | **2 ms ✅ 支持** |
| 输出：扬声器（Realtek） | 10 ms | **3 ms** | 10 ms ❌ 不支持 |

组合分析（I/O = 输入块 + max(输入,输出)×1.5 + 输出块）：

| 路线 | I/O | 含 DSP | 判定 |
|---|---|---|---|
| ① 现状：共享 / 共享（cpal） | 35.00 ms | 55.00 ms | ❌ |
| ② 输入 IAudioClient3 / 输出共享 | 27.00 ms | 47.00 ms | ❌ |
| ③ 输入共享 / 输出独占 | 28.00 ms | 48.00 ms | ❌ |
| **④ 输入 IAudioClient3 / 输出独占** | **9.50 ms** | **29.50 ms** | ✅ |

**关键点：只有双侧同时优化才进得了线。** 单改一侧都停在 47~48ms ——
环形缓冲要按两者中较大的块取水位，慢的那侧会把快的那侧的收益吃掉。

### 4.2 实开验证

理论算得出不等于开得成，所以写了第二个探针 `wasapi-exclusive`
**真的去打开独占流**。结果：**双侧都在硬件最小周期上一次开成。**

| | 共享（cpal） | 独占（实开） | 协商出的格式 |
|---|---|---|---|
| 输入：麦克风阵列 | 480 帧 | **96 帧 / 2.00 ms** ✅ | **int16** |
| 输出：Realtek 扬声器 | 480 帧 | **144 帧 / 3.00 ms** ✅ | **int24-in-32** |

顺带发现：输入侧的独占最小周期**也是 2ms**，所以双侧都走独占就够了，
根本不用碰 IAudioClient3。

### ⚠️ 格式协商是个真问题

逐级试下来，**两侧都不接受 f32，而且接受的整数格式还不一样**：

```
输入：f32 ❌ → int24-in-32 ❌ → int24 ❌ → int16 ✅
输出：f32 ❌ → int24-in-32 ✅
```

所以格式转换层必须**按设备分别协商**，不能写死一种。
好在 `wasapi` crate 的 `is_supported_exclusive_with_quirks()` 会自动试
不同的声道掩码和格式变体 —— 这正是独占模式最容易无声卡住的地方。

### 4.3 选定方案：`wasapi` crate

原计划是"先试 miniaudio，不行再自写 WASAPI"。实际找到了更合适的：
[`wasapi`](https://crates.io/crates/wasapi) 0.24，MIT，出自 CamillaDSP 作者。

| | `wasapi` crate（选定） | miniaudio 绑定 | 自写 WASAPI |
|---|---|---|---|
| 语言 | 纯 Rust | C 库 + FFI | 纯 Rust |
| 独占 + 周期控制 | ✅ `EventsExclusive{period_hns}` | 需验证 | ✅ |
| 格式协商辅助 | ✅ 自带 quirks 处理 | 部分 | ❌ 自己踩 |
| 工作量 | **1~2 天** | 1~2 天 + C 工具链 | 3~5 天 |

**仅 Windows 不是问题** —— 项目本身也已收窄为仅 Windows。

### 4.4 接通实跑

| | cpal 共享 | **WASAPI 独占** |
|---|---|---|
| 输入块 / 输出块 | 480 / 480 帧 | **96 / 144 帧** |
| I/O 延迟 | 35.00 ms | **9.50 → 14.50 ms**（水位修正后） |
| 端到端 | 55.00 ms ❌ | **29.92 ms ✅** |
| 时钟漂移 | 0 ppm | **-56 ppm，已补偿** |

## 5. ✅ CPU 余量：YIN 改 FFT 自相关

### 问题

块大小从 480 降到 144，每回调预算也从 10ms 压到 3ms。
平均占用没变（都是 15%），但**峰值几乎顶满**。

**根因**：YIN 每 256 个样本跑一次，**与回调块大小无关**。
输出块只有 144 帧，于是大约每 1.8 次回调就要扛一次完整的 YIN ——
负载是"块状"的，不是均摊的。原实现的互相关项是 O(W × τ_max) 直接求和，
约 686 × 643 ≈ **441k 次乘加**。

已排除启动瞬态：30 秒 862 次超半预算、60 秒 1417 次，持续发生。

### 做法

互相关改走 FFT，整体降到 O(W log W)。实现要点（`voice-core/src/fft.rs`）：

- **自己写，不引 rustfft** —— `voice-core` 刻意零依赖，将来要原样复用为
  CLAP 插件核心。需求也窄：定长、2 的幂、实数输入。
- **一次复数变换算两路实数 FFT**：把 a 放实部、b 放虚部做一次正变换，
  再靠共轭对称性拆出来。朴素做法要三次变换，这样只要两次。
- **FFT 长度必须 ≥ W + τ_max + 1**，否则循环卷积会绕回来污染低 lag ——
  那会表现为"某些音高莫名其妙检测错"，极难排查。有测试守着。

### 效果（60 秒实测，独占后端）

| | 改之前 | **改之后** | |
|---|---|---|---|
| 平均耗时 | 458 µs（15%） | **98 µs（3%）** | 4.7× |
| **峰值耗时** | 2626 µs（88%） | **790 µs（26%）** | 3.3× |
| 超过半预算的回调 | 1417 次 / 60 秒 | **0 次** | — |

**正确性防线**：被替换掉的直接求和保留为测试基准，
新旧两条路径的差分函数逐点比对（相对误差 < 1e-3），
另有一条测试直接比对最终检测音高（偏差 < 20 cents）。

> 附带收获：CPU 余量宽裕之后，`f0_floor` 的取值重新变成**纯粹的音质决策**。

## 6. 🔴 10 分钟连测：抓到三个 60 秒测不出来的问题

**这一项是投入最大、收获也最大的。** 60 秒和 180 秒全绿的配置，
在 10 分钟下暴露了三个问题，其中两个是真 bug。

### 🐛 bug 1：环形缓冲目标水位漏算了采集块

水位按**渲染块**算：144 × 1.5 = 216。但渲染一次取走 144，只剩 **72** ——
**比一个采集周期（96）还小**。采集线程晚到一拍就必然 xrun。

10 分钟实测 21 次。60 秒一次都看不到。

修正后：`目标水位 = 渲染块 × 系数 + 一个完整采集块`。延迟公式同步修正。

### 🐛 bug 2：压测 harness 会给"假绿"

改采集循环时用了 `get_next_packet_size()` —— 那是**共享模式**的概念，
独占模式下不返回有效值，结果采集读成 **0 帧**。

而整整 10 分钟跑下来，报告显示 **"本轮通过"**：

```
xrun 0 / overflow 0 / DSP 欠载 0 / 漂移 0 ppm / CPU 0%
```

**死掉的引擎在所有健康指标上看起来比健康的还完美。**

已修：判定的第一条改为**吞吐量检查**，输入或输出帧数不足预期一半直接判负，
并明确提示"下面的指标全部无效"。这条比它挡住的那个 bug 更重要。

> 独占模式下的正确做法：直接读，读到 0 帧为止，上限 4 次防跑飞。

### 📉 发现 3：29.5ms 这个数字错了两次

1. **公式错**：旧公式漏算水位里的采集块，同样配置的真值是 **31.5ms**
2. **配置错**：那个配置（水位 1.5）180 秒实测 **15 次 xrun**

两个错误恰好方向相反，才让它看起来"刚好卡线通过"。

### 缓冲深度对照实验

加了 `--target-fill` 做三档对照（各 180 秒）：

| 水位系数 | xrun / 180s | 水位最低 | 端到端 |
|---|---|---|---|
| 1.5 | **15** | 0（被抽干） | 26.92 ms |
| **2.5** | **0** | 265 | **29.92 ms** |
| 3.5 | 0 | 456 | 32.92 ms |

**2.5 是不产生 xrun 的最小值**，已设为默认。

### ✅ 时钟漂移补偿终于派上用场

之前几轮实测都是 0 ppm，我据此把双时钟风险降级为"有条件缓解"。

**这一轮第一次看到真实漂移：-39.3 ~ -55.9 ppm，插帧 1149~1731 次。**

原因正如预判：独占模式下音频流不再经过 Windows 混音器，
两台设备的时钟不再被统一。若不补偿，10 分钟会累积 **23.6 ~ 33.5 ms** 偏差。

补偿器压住了，残余 < 2 ms。**这个风险从"理论存在"变成了"实测存在且已解决"。**

## 7. 🔴 剩余 42 次 xrun：已定位，不是我们的代码

水位 2.5 在 180 秒下 0 次，**600 秒下 26~42 次** —— 事件是聚集的，
短窗口测不出来。这再次印证：**10 分钟不是形式主义。**

加了两个指标专门查：**采集/渲染的回调间隔最大值与停顿次数**。再跑 10 分钟：

```
xrun 42
回调耗时 平均 123 / 峰值 950 µs（预算 3000，占 32%）
采集间隔 最大/正常   44294 / 2000 µs   停顿 3 次
渲染间隔 最大/正常   44756 / 3000 µs   停顿 4 次
```

**两个线程在同一时刻一起停了约 44 毫秒。**

| 证据 | 说明 |
|---|---|
| 两侧**同时**停顿 44ms | 代码 bug 只会影响一侧；同时停顿是系统级事件 |
| CPU 平均 4%、峰值 32% | 不是算不过来 |
| 实时优先级已成功提权（2/2） | 不是优先级没配 |
| 停顿仅 3~4 次，但每次造成 ~10~15 个 xrun | 44ms ÷ 3ms 块 ≈ 15，数量对得上 |

**44ms 的整机停顿，任何缓冲策略都救不了** —— 要扛住它得留 45ms 缓冲。

嫌疑：虚拟机宿主暂停、Windows 电源管理 C-state 切换、杀毒扫描、后台服务。

> **结论：延迟结论成立且已验证；稳定性结论待换机器复测。**
> 归因指标已就位，一跑就知道那台机器有没有同样的整机停顿。

## 8. 🔴 脉冲往返实测：本机做不了

### 三条路都断了

| 方式 | 结果 | 原因 |
|---|---|---|
| ① 物理回环线 | 不可用 | 手头没有 |
| ② 声学回环 | ❌ 不可靠 | **麦克风阵列是 Intel 智音，自带硬件回声消除**，正在主动抵消扬声器输出。20 轮只检出 4 次，离散度 36.86~252.80 ms |
| ③ 数字回环（虚拟声卡） | ❌ 不可用 | 本机只有"网易虚拟音频设备"，其输入与输出**不互通** |

那个 36.86 ms 的最小值与理论值 + 声程大体吻合，但样本量 4、离散度 7 倍，
**不足以作为结论**，不写进验收数字。

### 🐛 顺带找到一个会影响所有用户的 bug

原来的脉冲是「逐样本交替极性的方波」。看着挺像回事，实际上
**那等于 24kHz —— 正好落在奈奎斯特频率上**。

- 数字回环线：能测到（纯数字通路不滤波）
- **声学回环：完全测不到** —— 扬声器放不出 24kHz，语音麦克风更收不到

也就是说：**凡是没有回环线、只能耳机贴麦的用户，延迟测量一次都不会成功**，
而且报错只说"超时"，根本查不出原因。

已改为 **2kHz 正弦短促音**（3ms，突起 + 线性衰减收尾）。
改完立刻从 0/25 变成 4/20 —— 剩下的失败是 AEC 造成的，不是频率问题了。

> **教训**：测量工具本身也要被测量。这个 bug 单元测试抓不到
> （数字回环下它是对的），只有真的接上声学路径跑一次才会暴露。

### 顺带补的诊断

测不到时原先只说"超时"。现在会报**输入峰值 / 本底 / 阈值**三个数并分流原因。
另外修了：`--latency` 与 `--mute` 原先不能同时用（脉冲被静音增益一起归零）。
现在脉冲在增益之后注入 —— **耳返静音、脉冲照发**。

### 要拿到权威数字，需要什么

1. 一根 3.5mm 回环线（输出口 → 输入口），或
2. 一块外置声卡（多数支持硬件直通回环），或
3. 装 VB-CABLE 之类的虚拟回环驱动

```bash
wego-bench --backend wasapi --latency --rounds 50 --mute
```

判读：看**中位数**，不看单次；离散度 > 5ms 说明系统调度不稳。
声学测法记得扣掉声程（约 3ms/米）。

## 9. ✅ Tauri 外壳与诊断页（含一个集成 bug）

### 🐛 COM 套间冲突 —— 后果严重

独立的 `wego-bench` 里 `initialize_mta()` 一次成功。但 Tauri 外壳
**早就把主线程初始化成 STA 了**，于是它返回 `RPC_E_CHANGED_MODE (0x80010106)`。

早期代码把这个返回码当致命错误 → 独占模式启动失败 → **静默退回共享模式**：

```
29.92 ms  →  76.10 ms
```

差 2.5 倍，而且直接越过 50ms 的 DAF 阈值 —— 产品在那一档是失效的。
而日志只有一行提示，UI 上完全看不出来。

两处修复：

1. `RPC_E_CHANGED_MODE` 不再当错误 —— WASAPI 的实际工作都在自己 spawn 的
   线程上，主线程是什么套间根本不影响。
2. **退回原因上报到 `BackendInfo.fallback_reason`**，UI 用红色横幅明确告知。

> **这个 bug 说明**：`wego-bench` 全绿不代表产品没问题。
> 外壳会改变运行环境（COM 套间、线程模型），
> 必须有一条在**产品可执行文件里**跑的验证路径。

### 🐛 重启太快抢不到独占设备（前端升级时顺带发现）

杀掉旧进程后**立刻**重启，独占设备还没被系统释放，首次尝试必然失败，
于是静默退回共享模式：

```
29.92 ms  →  76.5 ms
```

而「刚重启应用」恰恰是最常见的场景 —— 改个设置、崩溃重开、开发时反复启停。

**发现过程有点侥幸**：升级前端依赖后跑回归，看到窗口标题显示 76.5ms，
一度以为是 React 19 引入的问题。查下来跟前端无关，是我自己的测试脚本
`Stop-Process` 之后立刻 `Start-Process` 造成的竞态 ——
**但这正是用户会遇到的场景，脚本只是先撞上了。**

已修：独占模式失败时退避重试 4 次（150 / 300 / 450 ms），
盖住设备释放的窗口再考虑降级。代价只是失败时启动慢一点点。

> 顺带说明这个 bug 为什么之前没被发现：窗口标题显示实时延迟这个功能
> 是为了**验证事件流**才加的，结果它成了第一个暴露这个竞态的东西。
> 把关键状态放到显眼处，收益经常来自意料之外的地方。

### 🐛 UI 假设自己是唯一能启动引擎的人

引擎归 Rust 侧所有，生命周期与页面无关。但前端只在「点了启动按钮」时才设
`info`，于是 `--autostart` 起来的引擎、或页面刷新后仍在跑的引擎，
UI 一律显示「引擎未启动」。已修：挂载时先 `engineInfo()` 查一次既有状态。

### 验证手段：不靠截图

合成鼠标点击既脆又不可靠。改用两条确定性路径：

**① `--selftest`** —— 不开窗口，走一遍 UI 实际用的那条路
（`AppState::start → tick → stop`），断言设备枚举非空、空闲 tick 安全、
启动后输入输出帧数均 > 0、**序列化 JSON 含全部关键字段**、停止后干净。

```
启动         WASAPI 独占模式 / 输入 96 帧 / 输出 144 帧 / 29.92 ms
运行 tick    输入 158592 帧 / 输出 164160 帧 / 水位 451 / 目标 456
序列化       819 字节，关键字段齐全 ✓
✅ 自检通过
```

**② 窗口标题反映实时状态** —— 前端把延迟与 xrun 写进标题，
从进程外就能读到事件流是否真的在跑：


标题持续更新且无 xrun 后缀 → **command + event + window API 三条路全通**。
这对工具本身也有用：最小化后能从任务栏直接看到延迟和 xrun。

数字一致。两者相减即 Tauri 外壳的净开销。

## 10a. ✅ 噪声门：VAD 冻结的本底跟踪

### 起因

`YinConfig::silence_rms` 写死 `1e-4`（≈ **-80 dBFS**），
而实测本底是 **-54 dBFS** —— **阈值比真实本底低 26 dB，形同虚设**。

后果不是"听得到底噪"，而是：

- 风扇、变压器电流声有周期成分 → YIN 给出自信的基频 → **PSOLA 对着风扇修音**
- 噪声抬高 aperiodicity → 浊音误判清音 → **修音时断时续**

### 做法

抄实时通话产品的公版：**非人声帧更新噪声估计，人声帧冻结**。
冻结是关键 —— 唱歌是持续信号，无脑跟随的估计会被长音一路抬到人声电平。

非对称时间常数：降得快（τ=0.15s）、升得慢（τ=3s），
让 80ms 的清辅音抬不动本底（实测只抬 1.8 dB）。

### 🐛 两个自己挖的坑，都被实测抓到

**坑 1：一开机就在唱 → 门永远打不开。**
本底把歌声学了进去，阈值升到人声电平之上，用户表现是"启动完毫无反应"。

修法是一条原则：**失败要朝开的方向倒。** 本底高过 `MAX_PLAUSIBLE_FLOOR`
（-34 dBFS）就判定"估不准"，门直接失效、一律放行，退回 YIN 自己的判据。
漏掉一次风扇误触发只是瑕疵，把人声整段吞掉是产品事故。

**坑 2：启动时的数字静音被当成房间本底。**
cpal 共享模式启动慢，观察期内采集流还在预热、送的是全零。
最小值跟踪把 0 学成本底 → 钉死在 -100 dBFS → 门永远开着；
此时只要 YIN 把某段噪声判成浊音，本底就**永久冻结**在错值上。

实测三轮里抓到两轮正好 -100.0 dBFS 才发现。修法：`rms <= 1e-5` 直接丢弃，
真实房间噪声不可能恰好是 0。

> 注意坑 1 的防线只防"估高"，防不了"估低" —— 两个方向都要各防一次。

### 效果：静音时 CPU 降到 1/7

门关着就**根本不跑 YIN**（YIN 是这条链路上最贵的一项）。

| 配置 | 平均回调耗时 | 峰值 |
|---|---|---|
| 门开（12 dB） | **9~10 µs** | 136~435 µs |
| 门关（0 dB，YIN 常跑） | 70~75 µs | 603~1039 µs |

⚠️ 这是**安静时**的数字。唱起来门就开了，成本回到原样。
但安静（调设备、两条之间、说话间隙）占实际使用时间的大头。

### ❌ 顺带证伪了一个假设

原本怀疑：WASAPI 独占绕过 Windows 音频引擎 → 系统/厂商的 APO 降噪失效
→ 独占模式更吵。把本底读数做进 soak 报告之后实测：

| | 第 1 轮 | 第 2 轮 | 第 3 轮 | 离散度 |
|---|---|---|---|---|
| 独占 | -54.1 | -54.9 | -53.0 dBFS | **1.9 dB** |
| 共享 | -77.8 | -48.6 | -52.9 dBFS | 29 dB |

**不成立。** 独占不但没更吵，还更干净、更稳定。
最可能的解释是这块麦克风阵列（英特尔智音）的降噪做在硬件/固件里、位于 OS 之下，
两种模式都生效；共享模式自己引入了重采样与引擎处理的波动。

> n=3、一台机器、一只麦克风 —— 这是"在这台机器上不成立"，不是普遍结论。
> 换外置声卡复测时应当重跑。

## 10c. ✅ 频谱倾斜：补上声线的第二个维度

`timbre::match_to` 一直能测出倾斜差（合成素材上到 5 dB/八度），
但引擎里没有环节能施加它 —— **测得出、补不了**。
这是纯 DSP 路线离"真的像"最主要的缺口，比共振峰估计那 20% 的偏差大得多。

### 结构：两级（单极点低通 + 互补高通）

```text
lp[n] = lp[n-1] + a·(x[n] − lp[n-1])
hp[n] = x[n] − lp[n]
y[n]  = g_lo·lp[n] + g_hi·hp[n]
```

**一级不够。** 单极点过渡是 S 形，在 4.9 个八度上做不出直斜率：
实测要 -3.5 dB/八度只给到 -2.83（81%）。把支点摆到频带的 1/3 与 2/3
（622 Hz / 1934 Hz）、各担一半，过渡接力之后就直了。

### 标定是实测出来的，不是推导的

"多少 dB 档位差 = 多少 dB/八度"取决于支点与分析频带，
解析式和 `timbre::analyze` 实际量到的不是一回事：

| 版本 | 标定系数 | 实测 |
|---|---|---|
| 单级，初值 | 2.30 | 要 +2.0 → 得 +3.01 ❌ |
| 单级，修正 | 1.528 | ±2.0 准，-3.5 → -2.83 ❌ 压缩 |
| **两级** | **1.30** | **±2.0 与 ±3.5 全部落在 ±0.6 内** ✅ |

有测试钉死（`calibration_matches_measurement`）：改支点、改频带、
改 `timbre` 栅格都会在那里露馅。

### 代价：延迟 0，CPU 测不出来

纯 IIR，无缓冲 —— 输出第 n 个样本只依赖输入第 n 个样本。
有断言守着（`tilt_does_not_change_latency`）。

`bench dsp -d 20`，块 144 帧：

| 配置 | 平均 | P99 |
|---|---|---|
| 关 | 51.9 µs | 140.6 µs |
| 倾斜 +3 | 48.2 µs | 140.8 µs |
| 倾斜 +3 且共振峰 +4 | 50.6 µs | 138.2 µs |

三组无差异，全在运行间波动范围内 —— 每样本 6 次乘加，
相对 YIN + PSOLA 可以忽略。

### 闭环终于合上了

`applying_the_suggestion_closes_the_gap`：量出倾斜差 → 施加 →
重新量，残差必须降到原来的 40% 以下。这条把"量"和"施加"两侧钉在一起，
任何一侧的定义漂了都会失败 —— 而那种失败在产品上的表现是
**"点了应用，听起来没变"**。

## 10b. ✅ 声线模拟：共振峰平移的真实代价

「角色」功能靠**共振峰平移**塑造声线（见实施方案定调 #23/#24）。
两个问题必须先回答：加不加延迟、吃不吃 CPU。

### 延迟：不加，一毫秒都不加

PSOLA 的输出音高只由**合成标记的间距**决定，与颗粒内容无关。
把颗粒本身按 α 重采样，缩放的是频谱包络（共振峰），音高原封不动。
唯一代价是取样跨度从 ±T 变成 ±T·α。

延迟预算 `2×max_period` 每侧只留了 `max_period` 的余量，所以
**α 不能无限大**。但平时 T 远小于 max_period（f0=200Hz 时 T=240，
而 130Hz 下限给了 369），α 到 1.5 都够用；只有唱到贴近基频下限时才顶到边界。

顶到边界时按 `max_period / T` **就地收窄** —— 低音的声线变形平滑变弱，
而不是加延迟、也不是破坏延迟不变式。有回归用例守着这条
（`extreme_formant_near_f0_floor_stays_safe`、`formant_shift_does_not_change_latency`）。

### CPU：+7% 平均 / +19% P99，占回调预算 5%

α=1 走整数快路径（顺带保证不变调时逐位可复现）；α≠1 才做逐样本线性插值。

`bench dsp -d 30 --f0-floor 130`，块 144 帧、预算 3000 µs、合成浊音：

| 角色 | 平均 | 中位 | P99 | 占预算 P99 |
|---|---|---|---|---|
| 原声（α=1，整数路径） | 46.0 µs | 69.6 | 128.1 | 4.3% |
| 共振峰 +4（插值路径） | 49.2 µs | 68.9 | 152.4 | 5.1% |
| 移调 +5 / 共振峰 +6 | 46.5 µs | 70.4 | 133.4 | 4.4% |

**结论：便宜。** 声线是这套 DSP 里性价比最高的一个维度 ——
不加延迟、几乎不加 CPU，而听感变化明显。

### ⚠️ 这条结论差点被测错

第一次是拿 `soak`（真实麦克风）测的，共振峰那轮报了 14 次 xrun，
看起来像是"声线太贵"。复跑两轮都是 0 —— 是这台机器的整机停顿（见 §7）。

更要命的是：**那组对比从一开始就没有意义**。没人对着麦克风唱，
信号判为清音，PSOLA 走透传，`overlap_add` 一次都没执行。
测的是一条根本没跑到的代码。为此新增了 `bench dsp` 子命令，
离线喂合成浊音（冲激串过二阶谐振器 —— 纯正弦没有频谱包络，
测不出共振峰的开销）。

```
  fft.rs               自写定长基-2 FFT（一次复变换算两路实数 FFT）
  yin.rs               YIN 基频检测，互相关走 FFT（含新旧路径交叉验证）

  backend/cpal_backend.rs     共享模式兜底

  bin/wasapi_probe.rs         查硬件周期能力
```

**后端抽象的关键决定**：cpal 是回调驱动、WASAPI 独占是线程驱动，两者结构相反；

所以边界划在「后端只管把单声道 f32 喂进来 / 取出去」——
`duplex.rs` 只有一份，第二个后端不会把坑再踩一遍。
