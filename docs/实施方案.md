## 0. 一页纸摘要

**产品**：一个 **Windows 单机桌面工具** —— 实时修音监听 + 离线音色转换。
唱的时候耳返里听到修准的自己；唱完把干声换成目标音色，导出可用的音频文件。

> **平台：仅 Windows。** macOS 与 Linux 都不做（定调表 #2）。
> 低延迟路线（WASAPI 独占）是 Windows 特有的，换平台等于从零再验一遍。

**给谁**：坐在电脑前、戴耳机或接声卡、**要把唱的东西做成成品**的人 ——
翻唱创作者、内容/播客作者、自弹自唱的人、想练音准的人。

**不是**大众社交型 K 歌（手机场景，明确不覆盖），**也不是**面向小白的消费级 App。

### 「工具」定位意味着什么

这是一次**明确的定位收窄**，不是措辞调整。工具和消费级 App 在功能取舍上是相反的：

| | 消费级 App（原定位） | **桌面工具（现定位）** |
|---|---|---|
| 核心指标 | 留存、分享率、付费转化 | **出活效率**：从开唱到拿到可用文件有多快 |
| 参数 | 藏起来，给两个预设档 | **全暴露**，可调可存预设 |
| 成长感 | 打分、进步曲线、成就 | 不做。工具不负责激励用户 |
| 文件 | App 内的"作品"概念 | **就是本地文件**，拖进拖出，分轨导出 |
| 上手 | 引导流程、新手教学 | 一页说明 + 合理默认值 |
| 硬件要求 | 尽量迁就（蓝牙也得能用） | **可以要求有线耳机/声卡**，目标用户本来就有 |
| 交互 | 鼠标为主，动效 | 键盘快捷键、拖拽、批量、可脚本化 |
| 传播 | 产品内分享链路 | 用户自己拿文件去发，不管 |

**最重要的一条连锁反应**：工具用户**本来就戴有线耳机、很多人有声卡** ——
这让 WASAPI 独占模式（运行时独占声卡）从"普通用户不能接受"变成"目标用户的常态"。
**没有这次定位收窄，唯一能进 30ms 的方案是不可接受的。**

**技术骨架**：Tauri 壳 + React UI ｜ Rust 实时音频（FFT-YIN + TD-PSOLA）｜
Rust 本地推理（ONNX Runtime + WavLM + 声码器）

|---|--------|---------|------|---------|
| 0 | **产品定位** | **桌面工具**，非消费级 App ✅ 已确认 | 出活效率优先于留存与传播；参数全暴露；可要求有线耳机/声卡 | — |
| 1 | 产品形态 | **单机桌面工具，运行时离线** | 边际成本归零、隐私可当卖点、规避音乐版权分发 | — |
| 2 | 首发平台 | **仅 Windows** ✅ 已收窄 | macOS 与 Linux 都不做。集中资源打透一个平台；低延迟路线已在 Windows 验证落地 | — |
| 2b | macOS | **搁置，不排期** | 后端抽象层已留好位置，将来接 CoreAudio 不必改 DSP 与 duplex | 有明确商业理由再说 |
| 3 | 目标用户 | **要把唱的东西做成成品的人**：翻唱创作者 / 内容作者 / 自弹自唱 / 练音准 | 定位为工具后，用户画像从"怕麻烦的小白"换成"愿意调参数换质量的人" | — |
| 4 | UI 技术栈 | **Tauri 2 + React + Vite + TS** ✅ 已最终确认 | ⚠️ **理由已两次收窄**：不再是"消费级亲和力"（定位改工具），也不再是"一套码跨平台"（只做 Windows）。**当前成立的只剩两条**：React 生态开发效率、canvas 自绘音高条的成熟度。热路径本就在 Rust，换纯 Rust GUI 无性能收益 | **无。不再评估 Iced / Slint / 纯 Rust GUI** |
| 5 | 诊断 UI | **Tauri + React 内实现，与主 App 同一工程** ✅ 已确认 | 工具定位下它不只是"无遥测的替代品"，而是**用户要用的正经功能**：设备选择、缓冲大小、实测延迟 | — |
| 5b | 测量环境隔离 | **同一 binary 的 headless bench 模式**（`--bench` 跳过 WebView） | 承担「干净基线」职责，无代码重复，可做同源对比 | — |
| 6 | 实时音高检测 | **YIN**，互相关走 FFT | 低延迟 + 倍频错误少；FFT 把回调峰值从 88% 降到 26% | — |
| 7 | 实时音高修正 | **TD-PSOLA** | 延迟仅 1~2 个基频周期，经典 Auto-Tune 路线 | — |
| 8 | 音频 I/O | **`wasapi` crate（独占）主力 + cpal（共享）兜底** | cpal 硬编码共享模式，块周期改不了 → 55ms，不可用 | — |
| 8b | **低延迟后端** | **允许要求 WASAPI 独占 / ASIO / 外置声卡** ✅ 工具定位新增 | 独占模式"抢走系统声音"对工具用户是可接受代价，对消费级用户不是 | — |
| 8c | 蓝牙设备 | **明确不支持实时耳返**，只给提示 + 视觉反馈 | 物理限制，编解码延迟 100~250ms | — |
| 9 | 参考音高来源 | **自动调性检测（chroma + K-S）+ 手动改调兜底** | 零内容成本，支持用户导入任意伴奏 | — |
| 10 | 曲库 | **不做**。用户导入本地音频文件 | 单机无分发通道，且人工成本高 | — |
| 11 | 推理运行时 | **ONNX Runtime (`ort`)**；Win→DirectML，CPU 兜底 | DirectML 覆盖全部显卡，单机分发最省心 | — |
| 12 | 内容编码器 | **WavLM（MIT）** | 许可证干净，Base+ 仅约 95M，直接缩小审计范围 | 源音色泄漏实验不通过 → 回退 ContentVec（需审计） |
| 13 | 降噪预处理 | **NSNet2（CC BY 4.0）** | 官方 ONNX 权重，极轻量，署名即可商用 | — |
| 14 | 音色解码/声码器 | **轻量优先（DDSP-SVC 路线）**，⚠️ 待审计确认 | 这是许可证审计的**唯一剩余焦点** | 审计不通过 → 自训练声码器 |
| 15 | 实时换声 | **不做** | SVC 推理延迟百毫秒级，装不进 30ms 预算 | — |
| 16 | 音色来源 | **自录配音演员 + 签署覆盖 AI 训练与衍生用途的授权** | 名人音色是法律红线且泄漏无法回收 | — |
| 17 | 用户自训练音色 | **v1 不做** | 法务风险 + 本地训练成本 | v2 重新评估 |
| 18 | 商业模式 | **一次性买断为主**，音色包 DLC 为辅 | 工具付费习惯就是买断。定位为工具后**主要价值是工具本身而非音色数量** | — |
| 18b | **CLAP 插件** | **升级为一级路线图项**（v1.1 / v2） | 工具用户就是 DAW 人群。`voice-core` 已按无宿主依赖设计，增量成本低 | — |
| 19 | 授权校验 | **离线激活码，一次性联网激活；不做强防盗版** | 强 DRM 投入产出比低，且伤体验 | — |
| 20 | 模型分发 | **壳 20MB 安装包 + 按需下载模型（静态 CDN）**；另提供完整离线安装包 | 1GB 安装包没人下；功能 A 零模型依赖，装完 10 秒可用 | — |
| 21 | 可观测性 | **内置音频诊断页 + 用户主动导出报告**；无遥测 | 单机形态 + 隐私卖点 | — |
| 22 | **仓库结构** | **`app/` + `site/` + `docs/`** ✅ 新增（见 §10） | 官网与应用是两套构建、两种受众，必须分开 | — |
| 23 | **「角色」为参数的组织单位** | **调 / 修正速度 / 移调 / 共振峰打成具名预设**，界面上不再有裸露的「调」 ✅ 新增 | 用户想的是"唱成少女音"这**一件**事，不是四个要分别拧的旋钮。角色库持久化在 `%APPDATA%/com.wego.voice/characters.json` | — |
| 24 | **实时声线模拟** | **共振峰平移（PSOLA 颗粒重采样）+ 整体移调**；⚠️ 明确**不承诺音色克隆** ✅ 新增 | 共振峰平移**不增加任何延迟**（音高由合成标记间距决定，与颗粒内容无关），实测 CPU 仅 +7% 平均 / +19% P99。"像某个指定的人"要神经声码器，受 #14 阻塞 | #14 审计通过且延迟可控 → 增加离线声线转换 |

**唯一保留的开放项**：#14 音色解码器的具体选型 —— 由许可证审计结论决定。
注意 #24 与 #15 一致：**实时**链路不上神经网络，声线靠纯 DSP 塑形；神经声码器只可能出现在"唱完一键换声"的离线路径上。

## 2. 产品定义

### 2.1 两个核心动作

| | 动作 A：实时校准耳返 | 动作 B：一键换声 |
|---|---|---|
| 用户感受 | 「我居然唱得上去」 | 「这是我唱的？」 |
| 技术本质 | 实时音高检测 + 修正 + 耳返 | 歌声音色转换（SVC） |
| 实时性 | **硬实时，端到端 < 30ms** | 离线，分钟级可接受 |
| 模型依赖 | **零**（纯 DSP） | 重（数百 MB） |
| 工具价值 | 唱得下去（当场可用） | 出得了活（成品可交付） |

> **关键含义**：A 零模型依赖 → 装完立刻能开唱，不必等模型下载。这条保留。

### 2.2 V1 功能范围（P0，工具定位）

**核心链路**
1. **拖拽导入**本地伴奏（MP3/WAV/FLAC）+ 自动调性检测 + 手动改调
2. 实时 autotune 耳返，**完整参数面板**（retune speed / 调式 / 音域 / 修正上限），可存取预设
3. 实时音高条 + 音准柱（canvas 自绘）
4. 录音，**落盘保留原始干声**
5. **音频设备面板**：设备选择、缓冲大小、后端模式、实测延迟、xrun 计数
6. 本地音色转换，3~5 个自有授权音色，按需下载
7. **导出**：干声 / 修音后人声 / 换声后人声 / 合成混音 —— **可分轨**，WAV 优先，带 AI 生成标识与水印

**工具属性**
8. **会话文件**：保存/重开一次录制的全部状态
9. **批量换声**：选一批干声文件，排队跑，后台出结果
10. **键盘快捷键**：录制 / 停止 / 重录 / 切旁路 A-B 对比

### 2.3 明确不做（v1）

**技术/范围**
❌ 服务端 / 账号 / 云同步 ❌ 用户自训练音色 ❌ 实时换声 ❌ 内置曲库 / MIDI 参考旋律
❌ 本地人声分离 ❌ macOS / Linux ❌ 移动端

**因定位为工具而砍掉（原 P0，现移除）**
- ❌ **音准得分 / 进步可视化 / 成就** —— 工具不负责激励用户
- ❌ **本地"作品"历史库** —— 改为普通文件 + 会话文件
- ❌ **产品内分享链路** —— 导出文件即可
- ❌ **新手引导流程** —— 一页说明 + 合理默认值
- ❌ **蓝牙耳机的专门降级体验设计** —— 降为一条明确警告

## 3. 技术架构

### 3.1 总图

```
┌──────────────────────────────────────────────────────┐
│  WebView  —  React + Vite + TS                        │
│  导入伴奏 / 录制 / 音高条 / 音色选择 / 诊断页            │
│  ⚠ 不持有任何音频采样点                                │
└────────────▲───────────────────────┬─────────────────┘
             │                       │
   Event (20Hz 标量快照)       Command（低频）
             │                       │
┌────────────┴───────────────────────┼─────────────────┐
│  Rust  —  控制线程（tokio）          │                 │
│  会话状态机 / 伴奏解码 / 调性检测 / 干声落盘            │
└────────────▲───────────────────────┼─────────────────┘
             │                       │
   rtrb（无锁 SPSC）          spawn_blocking
             │                       │
┌────────────┴─────────────┐  ┌──────▼──────────────────┐
│ Rust — 实时音频线程        │  │ Rust — 推理工作线程      │
│ 采集→YIN→PSOLA→耳返       │  │ ort / ONNX Runtime      │
│ ⚠ 无分配/无锁/无日志/无panic│  │ 分钟级耗时，可取消       │
└──────────────────────────┘  └─────────────────────────┘
```

### 3.2 三条架构红线（违反即返工）

| # | 红线 | 原因 |
|---|------|------|
| 1 | **实时音频路径 100% 在 Rust 侧，采样点绝不过 WebView 或 IPC** | 48kHz/144 帧 = 每秒 333 次回调、每次 3ms 预算；Tauri IPC 是 JSON 过 bridge，必崩。IPC 只传控制信号和 20Hz 标量 |
| 2 | **落盘保存的必须是原始干声**，修正音只用于耳返监听 | 换声走「原始干声 + 离线精修」质量远好于对已修正音再修一次 |
| 3 | **推理线程绝不与实时音频线程抢 CPU** | 录制会话进行中时换声任务排队不启动，UI 上串行化 |

### 3.3 延迟预算（生命线）

**人耳容忍度**：< 20ms 自然 ｜ 20~50ms 可接受 ｜
**> 50ms 触发 DAF（延迟听觉反馈）效应，用户会不自觉结巴跑调，产品比不开更糟**

**生产配置实测**（详见 [Phase0-实测记录.md](./Phase0-实测记录.md)）：

```
输入块（WASAPI 独占）       96 帧    2.00 ms
环形缓冲水位（2.5×144+96）  456 帧    9.50 ms
输出块（WASAPI 独占）      144 帧    3.00 ms
────────────────────────────────────────
设备 I/O 小计              696 帧   14.50 ms
PSOLA 算法延迟（f0=130Hz）          15.42 ms
────────────────────────────────────────
端到端                              29.92 ms  ✅
```

⚠️ **水位与 f0_floor 是耦合的**：水位 2.5 是实测不产生 xrun 的最小值，
它占掉 14.5ms 后，30ms 预算只剩 15.5ms 给 DSP，对应 `f0_floor ≥ 约 130Hz`。
**想要更好的男低音音质（更低的 f0_floor）就必须接受超过 30ms。两者不可兼得。**

### 3.4 修正策略（决定「像人」还是「像机器」）

- **retune speed**：0ms = 电音（卖点之一），20~80ms = 自然不露痕迹 → 给滑杆
- **保留颤音**：4~7Hz 的 f0 调制是 vibrato，必须保留，否则唱出来像 MIDI
- **量化到调内音**而非十二平均律全部音
- **修正上限**：跑调 > ±300 cents 时不硬拉
  （⚠️ 调式量化下这个上限触发不了，详见 `scale.rs` 注释，它是为 Phase 2 的参考旋律预备的）

|---|------|------|------|
| UI | 主界面 | Tauri 2 + React + Vite + TS | ✅ 锁定 |
| UI | 音高条渲染 | `<canvas>` + rAF + ref 直绘，**不走 React state** | ✅ 已实现 |
| UI | 诊断页 | React（主 App 内的一个路由） | ✅ 已实现 |
| UI | 基线测量 | headless bench 模式（`--bench` 跳过 WebView） | ✅ 已实现 |

| 音频 | 兜底 I/O | `cpal` 0.18（共享） | ✅ 已实现 |
| 音频 | 跨线程 | `rtrb`（无锁 SPSC） | ✅ |
| 音频 | 线程提权 | `audio_thread_priority` | ✅ |
| DSP | FFT | **自写定长基-2**（零依赖，一次复变换算两路实数 FFT） | ✅ |
| DSP | 音高检测 | **自写 YIN**，互相关走 FFT | ✅ |
| DSP | 音高修正 | **自写 TD-PSOLA** | ✅ |
| DSP | 调性检测 | 自写（chroma + Krumhansl-Schmuckler） | ⬜ 待做 |
| 推理 | 运行时 | `ort`（ONNX Runtime）+ DirectML | ⬜ 待做 |
| 工程 | 命令行 | `clap`（derive + 子命令 + global 参数） | ✅ |
| 工程 | 日志 | `log` + `env_logger` | ✅ |

> ⚠️ **日志与输出必须分开**：报告表格是程序输出（`println!`），
> 警告错误是诊断信息（`log::*`）。混在一起会导致结果被日志级别过滤掉。
>
> ⚠️ **音频线程内绝不打日志** —— 违反实时纪律（分配 + 取锁 + IO）。
> 相关信息通过原子量上报给控制线程。

| **音色解码 + 声码器** | DDSP-SVC 路线 | ⚠️ **待审** | 🔴 **审计唯一焦点** |

**结构性认知**：微软开源了流水线的**前半段（编码/理解）和运行时**，
但**没有开源歌声生成模型**。待审范围已收敛到「解码器 + 声码器」这一段。

**已排除**：Phi-4-multimodal（只能听不能说）、VibeVoice（TTS 非 SVC，且上游曾下架）、
VALL-E / NaturalSpeech（无公开可商用权重）、Azure Speech（云服务）、
so-vits-svc（AGPL-3.0，与闭源商用硬冲突）。

### ⚠️ WavLM 的已知技术风险

WavLM 的设计目标之一是**保留说话人身份信息**（所以声纹验证很强），
而音色转换恰恰需要**去掉**源说话人信息。直接喂解码器会导致**源音色泄漏**。
对策：取特定中间层、加解耦训练、或走 kNN 检索式转换。**这是要做实验调的。**

## 9. 工程规范

### 9.1 两个纪律区（Code review 单独看）

**① `voice-core` 的 `process` 路径（`psola.rs` / `lib.rs`）—— 实时安全**

- 不 `Vec::push` / `Box::new` / `format!` → 所有 buffer 在构造时预分配
- 不 `Mutex::lock` → 一律 `rtrb` + 原子量
- 不 `println!` / `tracing::*` → 要打日志就塞进 ring buffer 让控制线程打
- 不 `unwrap()` → panic 在音频回调里是灾难

**② 将来的 `infer/preprocess.rs` —— 训练/推理对齐**

预处理必须与训练时**逐位对齐**（重采样、归一化、f0 插值与 UV 标记）。
对不齐的表现是「**能出声但音色不像**」，极难排查。必须配黄金样本回归测试。

### 9.2 复用设计：`voice-core` 零依赖

DSP 核心不依赖任何 I/O、后端或 GUI（连 FFT 都是自写的）。
成本几乎为零，但保留了第二条商业化路径：用 `nih-plug` 发成 **CLAP 插件**。

> 优先 CLAP（宽松许可）；VST3 的 SDK 是 GPLv3 / 商业双授权。

## 10. 仓库结构（v1.2 新增）

```
wego-voice/
├── app/          桌面应用（Tauri + React + Vite + TS + Rust workspace）
├── site/         官网（React + Vite + TS，独立构建、独立部署）
└── docs/         项目文档（两者共用，不参与任何构建）
```

**两边同栈（React + Vite + TS），但各自独立的依赖与构建。**
同栈降低一个人维护两边的心智成本；分目录保证官网改文案不必碰 cargo。

**为什么分开**：

| | `app/` | `site/` |
|---|---|---|
| 受众 | 已经装了工具的用户 | 还没听说过这东西的人 |
| 构建 | Tauri + cargo + vite → exe | 静态站 → CDN |
| 发布节奏 | 跟版本走 | 随时改文案 |
| 依赖 | Rust + Node | 只有 Node |

混在一起的代价：官网改个文案要跑 cargo、应用的 `node_modules` 和官网的搅在一起、
CI 每次都全量构建。分开之后两边互不影响。

`docs/` 放在根：它既不属于 app 也不属于 site，而且官网的内容
（延迟原理、硬件要求、FAQ）可以直接引用这里的实测数字。
