## 1. 想法拆解

原始想法包含两个独立产品动作，技术栈完全不同，要分开评估：

| # | 动作 | 用户感受 | 技术本质 | 实时性要求 |
|---|------|---------|---------|-----------|
| A | 唱的时候实时听到自己唱准了 | 「我居然唱得上去」 | 实时音高检测 + 音高修正 + 耳返（side-tone） | **硬实时，端到端 < 30ms** |
| B | 唱完一键换成想要的声音 | 「这是我唱的？」 | 歌声音色转换（SVC, Singing Voice Conversion） | 离线，本机推理，分钟级可接受 |

A 是「即时爽感」的来源，也是留存的关键；B 是「传播」的来源，也是付费点。
**A 难在工程（延迟），B 难在合规与分发（模型许可证 + 包体）。算法本身都不是瓶颈。**

### 单机形态带来的变化（v0.2 新增）

| 维度 | 影响 |
|------|------|
| ✅ 成本 | 无 GPU 推理成本、无服务器运维、无带宽。边际成本 ≈ 0 → **适合一次性买断 + 音色包 DLC** |
| ✅ 隐私 | 用户的声音不出本机，这是**可以拿来当卖点**的差异化 |
| ✅ 音乐版权 | 用户导入自己的伴奏文件，不涉及内容分发。**原 🟠 级版权风险大幅降低** |
| ❌ SVC 推理 | 必须跑在用户机器上，性能与包体成为新的一级问题（见 §3） |
| ❌ 模型许可证 | 权重随 App 分发出去，开源协议的传染性和商用限制会落到你头上（见 §4） |
| ❌ 音色资产 | 模型在用户硬盘上，**可被提取**，无法回收 |
| ❌ 曲库/参考音高 | 没有云端曲库，参考音高只能本地推导（见 §2.4） |
| ❌ 可观测性 | 没有遥测，延迟/爆音问题只能靠本地诊断 + 用户主动反馈日志 |

## 2. 动作 A：实时校准耳返

### 2.1 延迟预算（最关键的一张表）

人在唱歌时，自己的声音通过两条路径进入大脑：骨传导（0 延迟）+ 耳返（有延迟）。两条路叠加会出问题：

- **< 20ms**：感知为「自己的声音」，自然。理想区间。
- **20~50ms**：能察觉到「声音有点飘/有点空」，梳状滤波导致音色发闷，但不影响发声。可接受上限。
- **> 50ms**：进入**延迟听觉反馈（DAF）**效应区，人会不自觉地结巴、拖拍、跑调更严重。**产品直接失效，甚至比不开更糟。**

端到端链路的延迟构成（48kHz 采样）：

```
麦克风硬件采集 + 驱动缓冲    3 ~ 15ms   ← 平台/驱动决定
音高检测所需分析窗          10 ~ 30ms   ← 算法决定，有物理下限
音高修正处理                 1 ~ 5ms    ← PSOLA 很便宜
播放缓冲 + 硬件输出          3 ~ 15ms   ← 平台/驱动决定
──────────────────────────────────────
有线耳机合计                17 ~ 65ms
蓝牙耳机额外增加          100 ~ 250ms   ← 致命
```

**结论与对策：**

1. **蓝牙耳机（A2DP/SBC/AAC）场景 100% 做不了实时耳返**，这是编解码 + 无线协议的物理限制，任何算法都救不了。
   → 进入唱歌页时**检测音频输出设备**，是蓝牙则强制降级到「视觉反馈模式」（只看音高条，不听修正声），并明确提示「插上有线耳机体验完整效果」。这个降级体验要专门设计，不能当异常处理。
   → **桌面场景下这个风险比手机小得多**：台式/笔记本插有线耳机或用声卡是常态。这是选择桌面形态的一个额外红利。
2. **平台可控性**（桌面形态的核心优势）：macOS CoreAudio 稳定在 10ms 级；Windows WASAPI 共享模式 10~30ms，独占模式可更低。**没有 Android 那种机型离散灾难。**
3. **支持外置声卡/USB 麦克风** → 延迟和音质天花板都高出一截，专业用户体验极好。

> ⚠️ 这仍是整个项目唯一的「可能推翻立项」的风险点，但桌面形态让它从 🔴 降到 🟠。**第一周仍要做真机延迟验证。**

### 2.2 音高检测（F0 estimation）

| 方案 | 延迟 | 精度 | 算力 | 适用 |
|------|------|------|------|------|
| 自相关 / AMDF | 低 | 一般，易倍频错误 | 极低 | 不推荐 |
| **YIN / pYIN** | 低 | 好，倍频错误少 | 低 | ✅ **实时首选** |
| SWIPE' | 中 | 好 | 中 | 备选 |
| CREPE / RMVPE（神经网络） | 高 | 最好，抗噪 | 高 | ✅ **离线首选（给 B 用）** |

- 实时侧：**YIN**，帧长 1024~2048 samples，hop 5~10ms。
- 物理下限提醒：检测基频需要至少 2~3 个周期。男低音 F0≈80Hz → 周期 12.5ms → **窗口至少 25~37ms**。这意味着低音区的检测延迟天然更高。对策：按音域自适应窗长（高音区用短窗），或对低音区允许略高延迟（低音区跑调听感上也更不敏感）。
- 需要处理：清音/静音段（不修正，直通）、爆破音、伴奏串音（耳机漏音进麦克风 → 检测到伴奏的音高，必须做回声消除或要求封闭式耳机）。

### 2.3 音高修正（Pitch Correction）

| 方案 | 延迟 | 音质 | 结论 |
|------|------|------|------|
| **TD-PSOLA** | 极低（1~2 个基频周期） | 小幅修正（±200 cents 内）很好，大幅修正会「机器人味」 | ✅ **实时首选** |
| 相位声码器 | 中高 | 相位涣散，人声发「糊」 | ❌ |
| WORLD / 神经声码器 | 高 | 最好 | ✅ 离线精修可用 |

TD-PSOLA 正是经典 Auto-Tune 类产品的技术路线：时域切片、按目标周期重叠相加，算力低到可以跑在任何设备上。

**修正策略（决定「像人」还是「像机器」）：**
- `retune speed`（修正速度）：0ms = 电音效果（T-Pain），20~80ms = 自然「修得不露痕迹」。**给用户一个滑杆，因为电音本身也是卖点。**
- `保留颤音`：对 f0 曲线做频率分解，4~7Hz 的调制是 vibrato，要保留不要修掉，否则唱出来像 MIDI。
- `量化目标`：不要量化到十二平均律全部音，要**量化到当前调内音**（见 2.4），否则半音跑调会被修到错误的音上，听感更怪。
- `修正上限`：跑调超过 ±300 cents 时不硬拉（拉过去会严重失真），改为部分修正 + 视觉提示。这条对真·音痴很重要。

### 2.4 「唱准了」的参考从哪来（单机形态下的关键调整）

要判断「准」，必须有目标音高曲线。单机、用户自带伴奏的前提下：

| 方案 | 单机可行性 | 说明 |
|------|-----------|------|
| **① 调式约束（无参考）** | ✅ **v1 默认** | 本地做**自动调性检测**（chroma 特征 + Krumhansl-Schmuckler 之类，纯 DSP，轻量），得到 key 后把用户唱的量化到最近的调内音。零内容成本，支持任意导入的伴奏。**只保证「不跑调」，不保证「唱对音符」。** |
| ② 用户手动指定调 | ✅ 必备兜底 | 自动检测出错时（转调歌、非西方调式）让用户手动选 key，或提供「听两秒伴奏重测」 |
| ③ 从原唱提取参考旋律 | 🟡 v2 | 需本地人声分离（Demucs 类，又是几百 MB 模型）+ RMVPE 提 f0。质量最好但包体和耗时都涨 |
| ④ 内置 MIDI 曲库 | ❌ 不做 | 单机无曲库分发通道，且每首歌人工成本高 |

**建议：v1 = ① + ②**。这套方案的好处是完全不依赖曲库，用户拖进任何一首伴奏都能用 —— 这恰好是单机 App 该有的形态。

### 2.5 反馈的三个层次

- **听觉**：耳返里的修正后人声（核心爽点）
- **视觉**：实时音高条/音准柱，蓝牙降级时的唯一反馈
- **事后**：音准得分、跑调热力图 —— 这是「训练/进步」叙事的载体。单机 App 里这个本地历史记录很有价值（看到自己变好）

## 3. 动作 B：本地一键换声（SVC）

### 3.1 技术路线

成熟开源方案（均为「内容编码 + 音色解码」范式）：

```
干声 → 预处理（降噪/去混响/切片）
     → 内容编码（ContentVec / HuBERT，去掉音色只留发音内容）
     → f0 提取（RMVPE）
     → 目标音色解码（NSF-HiFiGAN 等神经声码器）
     → 后处理（EQ/压缩/混响）+ 与伴奏混音
```

候选：**DDSP-SVC（轻量、快、最适合本地分发）**、RVC 系（生态成熟、音色训练数据需求低）、so-vits-svc（质量好但重，且协议是问题，见 §4）。

**成熟度判断：算法本身不是研发风险**，开源社区已验证数年。**单机形态下的风险转移到了「跑得动吗」和「能合法分发吗」。**

### 3.2 本地推理：性能与包体（v0.2 核心新增）

**模型组成与粗略体积**（fp32，量化后可显著下降）：

| 组件 | 典型模型 | 量级 | 备注 |
|------|---------|------|------|
| 内容编码 | ContentVec / HuBERT | 数百 MB | int8 量化后体积和速度都大幅改善 |
| f0 提取 | RMVPE | 百 MB 级 | 可退回纯 DSP 的 pyin（慢但零模型） |
| 音色解码 + 声码器 | RVC generator / NSF-HiFiGAN | 几十~百 MB **每音色** | 多音色可共享主干，只换 speaker embedding |

**执行后端**（通过 `ort` = ONNX Runtime 绑定）：

- **Windows → DirectML EP**：✅ 首选，兼容 N卡/A卡/Intel 核显全覆盖，不挑硬件
- **Windows → CUDA EP**：更快但只支持 N 卡，且运行时包体大。作为可选加速
- **macOS → CoreML EP**：走 Apple GPU / Neural Engine，Apple Silicon 上表现好
- **纯 CPU 兜底**：一定要有，但**可能是分钟级**

> ⚠️ **必须实测的数字（第 3~4 周）**：一首 3 分钟歌在 ①主流独显 ②笔记本核显 ③纯 CPU 三档机器上的端到端耗时。
> 如果纯 CPU 超过 5 分钟，UI 必须做后台队列 + 进度条 + 可继续做别的事，并对低配机器默认只提供**轻量档（DDSP-SVC）**。

**包体问题（Tauri 的「小二进制」优势在这里消失）：**

```
Tauri 壳 + React 前端          ~10 ~ 20MB
ONNX Runtime + DirectML 运行时  ~100 ~ 200MB
模型权重（编码器+f0+若干音色）   ~400MB ~ 1GB+
────────────────────────────────────────
一次性打包                      ❌ 用户不会下载 1GB 的安装包
```

**对策（推荐）**：安装包只带壳（~20MB 秒装，装完立刻能用功能 A）；**首次使用换声时按需下载模型包**；每个音色做成独立的小包，用户选哪个下哪个。
这仍然是「单机 App」—— 运行时完全离线，只是模型有一次性下载。**但要在产品上想清楚：完全断网的用户第一次用不了 B 功能。** 或者提供「完整离线安装包」作为可选下载。

### 3.3 实时换声？不行

有人会问：既然有 SVC，能不能边唱边换声？
**不能。** SVC 的神经网络推理延迟在百毫秒量级（即使 GPU 上高度优化的实时 SVC 方案也在 100~300ms），远超耳返的 30ms 预算。硬塞进去会直接触发 DAF 效应。
**A 和 B 是两条独立链路，这个架构边界不要动摇。**

### 3.4 质量的决定因素不是模型，是干声

SVC 的输出质量高度依赖输入干声。必须在录音环节就保证：
- 耳机漏音的伴奏串进麦克风 → 换声后会出现「鬼影伴奏」→ **强制耳机，并做伴奏回声消除**
- 房间混响 → 需要去混响预处理
- 系统级自动增益/降噪（AGC/NS）会损伤音质 → 尽量用原始采集模式

**关键架构决定：动作 A 的修正音只用于耳返监听，落盘保存的必须是原始干声。** 换声走「原始干声 + 独立的离线精修音高」，质量远好于对已修正音再修一次。这条要在第一行代码前定下来。

## 4. 风险清单（v0.2 重排）

| 风险 | 等级 | 说明 | 对策 |
|------|------|------|------|
| **模型许可证（商用）** | 🔴 高 | **单机分发 = 权重随 App 发给用户**，开源协议的传染性和商用限制直接落到你身上。RVC 主仓库为宽松协议，但 so-vits-svc 为 AGPL-3.0（闭源商用硬冲突）；上游的 ContentVec / HuBERT / NSF-HiFiGAN 预训练权重各有条款，**部分为 CC-BY-NC（禁止商用）** | **在写第一行推理代码前**，把链路上每个权重文件和每个仓库的许可证列成表逐个核实。这件事排在技术验证之前。拿不准的一律换掉或自己训练。<br>✅ **已找到部分解法**：内容编码可改用微软 **WavLM（MIT）**、降噪用 **NSNet2（CC BY 4.0）**，能把待审范围缩掉约一半 —— 详见 [技术架构选型.md §6.5](./技术架构选型.md) |
| **耳返延迟** | 🟠 中（桌面形态下降级） | 蓝牙无解；Windows 共享模式卡在预算边缘 | 设备检测 + 视觉降级模式；第 1 周真机验证 |
| **本地推理性能 / 包体** | 🟠 中 | 低配机可能分钟级；全量打包 1GB+ 没人下 | 壳 + 按需下载模型；低配机默认轻量档；后台队列 UI |
| **音色权利** | 🟠 中 | 用名人/明星音色是红线。《民法典》第 1023 条明确自然人声音参照肖像权保护，国内已有 AI 声音侵权判决先例 | **只上架①自有录制并签署授权的配音演员音色 ②完全合成的虚拟音色**；授权合同需覆盖 AI 训练与衍生用途；**不做用户自训练音色**（v1） |
| **音色资产被提取** | 🟠 中 | 模型在用户硬盘上，可被提取用于其他工具。**无法根治** | 加密 + 运行时解密、自定义格式，只能抬高成本。**这反过来强化了「绝不碰名人音色」的结论 —— 一旦泄漏无法回收** |
| **滥用（伪造他人声音）** | 🟠 中 | 换声技术的固有风险，且单机无法做服务端管控 | 不提供任意声音克隆；输出嵌入不可听水印 + 文件元数据标识；符合 AI 生成内容标识要求 |
| **伴奏串音污染干声** | 🟠 中 | 直接影响 B 的成品质量 | 强制耳机 + AEC；无耳机时禁用录制或明确降质提示 |
| **无遥测，问题看不见** | 🟡 低 | 单机没有服务端日志，延迟/爆音问题靠用户报 | 内置「音频诊断」页（实测延迟、xrun 计数、设备信息），一键导出报告 |
| **音乐版权** | 🟡 低（降级） | 用户导入自己的伴奏，不涉及内容分发 | 不内置曲库；用户导入内容的使用责任在用户 |
| **真·失歌症人群** | 🟡 低 | 约 1.5~4% 人群为先天性失歌症（感知层面无法辨别音高），实时反馈对其**无效** | 承认边界；对这部分人价值退化为「录完直接修好」，仍然成立 |
| **「修得太狠不像我」** | 🟡 低 | 强修正会失真，用户反而不认 | retune speed 可调 + 保留 vibrato + 跑调过大时不硬拉 |

## 5. MVP 定义（单机版）

### 做（P0）
1. **导入本地伴奏**（MP3/WAV/FLAC）+ 自动调性检测 + 手动改调兜底
2. **实时 autotune 耳返**（YIN + TD-PSOLA），retune speed 两档（自然 / 电音）
3. **实时音高条**（蓝牙/高延迟设备时作为唯一反馈）
4. **录音，落盘保留原始干声**
5. **音频诊断页**：实测端到端延迟、设备列表、xrun 计数（代替遥测）
6. **本地一键换声**，3~5 个自有授权音色，按需下载模型包
7. **成品混音 + 导出本地文件**（带 AI 生成标识元数据 + 音频水印）
8. 本地历史记录 + 音准得分（进步可视化）

### 明确不做（v1）
- ❌ 任何服务端 / 账号 / 云同步
- ❌ 用户自定义音色克隆（法务风险 + 本地训练成本）
- ❌ 实时换声（见 §3.3）
- ❌ 内置曲库 / MIDI 参考旋律
- ❌ 本地人声分离提取参考旋律
- ❌ 社交 / 合唱 / PK
- ❌ Linux（社区版按需，见架构文档 §4.4）

## 6. 验证路径

**第 1~2 周：延迟尖刀（Go / No-Go 决策点 1）**

只回答一个问题：*Rust + cpal 端到端延迟能不能稳定压到 30ms 以内？*

## 附：一句话总结给决策者

「实时修音 + 事后换声」在技术上没有未知数，全是已验证的成熟方案。
改成单机后，**成本和版权风险大幅下降，但新增了两个必须先解决的前置问题：**

> **① 开源模型权重能不能合法地随 App 商用分发（这决定项目能不能做）；**
> **② 耳返延迟能不能在 Windows 上稳定进 30ms（这决定核心体验成不成立）。**

建议**第 1~2 周并行做这两件事**：一个人做延迟尖刀 demo，一个人做许可证审计。两个都过了，剩下的都是工程排期问题。
