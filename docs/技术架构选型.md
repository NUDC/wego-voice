## 结论

**可行，而且这是 Tauri 少见的「真优势场景」** —— 尤其在确定做单机之后，Tauri 从「一个可选项」变成了**相当契合的选择**：

| | |
|---|---|
| 🔴 **红线** | 实时音频路径 **100% 在 Rust 侧**，WebView 只负责 UI。一旦音频采样点经过 JS 或 Tauri IPC，项目就死了。 |
| ✅ **契合点** | 单机 = 全部算力在本地 = 需要一个高性能原生后端。Rust（无 GC、确定性、可跑 ONNX 推理）正好是这个后端，而 React 负责 UI 又保住了开发效率。 |
| 🟠 **新代价** | 本地跑 SVC 推理 → **Tauri「二进制小」的优势会被模型体积吃掉**，必须做按需下载（见 §6）。 |

桌面形态还顺带消灭了可行性文档里两个 🔴 级风险：**蓝牙耳机默认路径**和 **Android 机型离散**。代价是失去了移动端的用户规模和传播链路 —— 这是已经拍板的取舍。

## 1. 为什么 WebView 绝对不能碰实时音频

原可行性文档给的延迟预算是 **端到端 < 30ms**。WebView 音频栈做不到，原因是结构性的：

1. **WebAudio / getUserMedia 链路延迟 50~150ms 且不可控**。`latencyHint: 'interactive'` 只是建议，拿不到 buffer size 的控制权，拿不到独占模式。
2. **三套引擎行为不一致**。Tauri 用的是系统 WebView：Windows = WebView2(Chromium)，macOS = WKWebView，Linux = WebKitGTK。三者的 AudioWorklet 实现质量差距很大，WebKitGTK 尤其不可靠。你会在三个平台调三套 bug。
3. **JS GC 会造成爆音**。AudioWorklet 虽然跑在独立线程，但仍在 JS 堆上，一次 GC 停顿就是一次 xrun。实时音频要求的是**确定性**，不是平均性能。
4. **Tauri IPC 扛不住音频速率**。48kHz / 256 frames 的 buffer = **每秒 187 次回调**，每次回调有 5.3ms 预算。Tauri 的 command/event 是 JSON 序列化过 WebView bridge，单次开销就在百微秒到毫秒量级。每个 buffer 过一次 IPC，必崩。

> IPC 用来传**控制信号**（每秒几次）和**可视化数据**（每秒 30~60 次的 f0 标量）完全没问题。传**采样点**（每秒 187 次 × 256 个 f32）绝对不行。这条界线要刻在架构里。

## 2. 正确的分层

```
┌──────────────────────────────────────────────────────┐
│  WebView  —  React + Vite + TS                        │
│  导入伴奏 / 录制界面 / 音高条 / 音色选择 / 诊断页       │
│  ⚠ 不持有任何音频采样点                                │
└────────────▲───────────────────────┬─────────────────┘
             │                       │
   Event (30~60Hz)            Command (低频, 用户操作触发)
   { f0_hz, cents_off,         start_session / stop
     note, rms, clipping }     set_retune_speed / set_key
   + 换声进度事件               run_conversion
             │                       │
┌────────────┴───────────────────────┼─────────────────┐
│  Rust  —  控制线程（tokio async）    │                 │
│  会话状态机 / 伴奏解码 / 调性检测 / 干声落盘            │
└────────────▲───────────────────────┼─────────────────┘
             │                       │
   rtrb (lock-free SPSC)     原子参数 │ spawn_blocking
   ← f0 与电平上报            → retune│ (绝不占用实时线程)
             │                       │
┌────────────┴─────────────┐  ┌──────▼──────────────────┐
│ Rust — 实时音频线程       │  │ Rust — 推理工作线程      │
│ (cpal callback, 最高优先级)│  │ ort/ONNX Runtime         │
│ 采集→YIN→PSOLA→耳返       │  │ 内容编码→f0→声码器        │
│ ⚠ 无分配/无锁/无日志/无panic│  │ 分钟级耗时，可取消       │
└──────────────────────────┘  └─────────────────────────┘
```

> **两条链路完全隔离**：实时耳返（A）和换声推理（B）不共享线程、不共享缓冲。
> 推理必须走 `tokio::task::spawn_blocking` 或独立线程池，**绝不能和音频回调抢 CPU** —— 否则用户一边唱一边换声时会爆音。理想情况下换声任务在录制会话结束后才启动，并在 UI 上明确串行化。

**实时线程的纪律**（违反其中任何一条都会随机爆音，且极难调试）：

- 不 `Vec::push` / `Box::new` / `format!` —— 所有 buffer 在 `start_session` 时预分配
- 不 `Mutex::lock` —— 跨线程一律用 `rtrb` 环形缓冲 + `AtomicU32/AtomicBool` 参数
- 不 `println!` / `tracing::info!` —— 要打日志就把结构体塞进 ring buffer，让控制线程去打
- 不 `unwrap()` —— panic 在音频回调里是灾难，用 `saturating_*` 和显式兜底
- 建议加 `#[deny(clippy::disallowed_methods)]` + `assert_no_alloc` 类 crate 在 debug 下守住这条线

## 3. Rust 侧选型

| 职责 | 方案 | 成熟度 | 备注 |
|------|------|--------|------|
| 音频 I/O | **cpal** | ✅ 成熟 | 跨平台标准选择。坑见 §4.1 |
| 跨线程通信 | **rtrb** 或 `ringbuf` | ✅ | 无锁 SPSC，专为实时音频设计 |
| 音高检测 | `pitch-detection` crate（YIN / McLeod） | 🟡 够用 | 质量中等，大概率要自己重写或魔改 |
| 音高修正 | **自己实现 TD-PSOLA** | ❌ 无现成轮子 | ~300~600 行，算法文献充分，是本项目最核心的自研代码 |
| 伴奏解码 | **symphonia** | ✅ 成熟 | 纯 Rust，MP3/AAC/FLAC/WAV |
| 重采样 | **rubato** | ✅ 成熟 | 设备采样率不匹配时必需 |
| DSP 工具 | `fundsp` / `realfft` | ✅ | 滤波器、FFT |
| 调性检测 | 自己实现（chroma + K-S 算法） | ❌ 无现成轮子 | 纯 DSP，轻量，~200 行 |
| **本地 SVC 推理** | **`ort`（ONNX Runtime 绑定）** | ✅ 成熟 | 单机形态下**从可选变必选**，详见 §6 |
| 推理备选 | `candle`（纯 Rust）/ Tauri sidecar 挂 Python | 🟡 | candle 生态还在长；sidecar 方案包体更大但调试快 |
| 模型按需下载 | `reqwest` + 断点续传 + 校验 | ✅ | 唯一的网络依赖 |

**自研工作量诚实估计**：YIN + PSOLA + 实时调度这一块，是 **2~4 周的专门 DSP 工作**，不是搭个 crate 就完事。好在 Rust 做这个很舒服——无 GC、确定性析构、`std::simd` 可用。
本地推理集成（ONNX 导出 + 三后端适配 + 预/后处理对齐）另算 **2~3 周**，其中最容易踩坑的是**预处理必须和训练时逐位对齐**（重采样方式、归一化、f0 的插值和 UV 标记），对不齐的表现是「能出声但音色不像」，很难查。

## 4. Tauri 会坑你的地方（按严重程度排）

### 4.1 🔴 cpal 的输入和输出是两个独立的流、两个时钟

这是 cpal 最大的实践问题。你拿到的是两个独立的回调，中间必须用 ring buffer 桥接。两个设备的时钟**不完全同步**（标称 48000Hz 的设备实际可能是 48000.3Hz），长时间录唱会导致 ring buffer 水位单向漂移 —— 要么憋满（延迟越唱越大），要么饿死（爆音）。

**对策：**
- 监控 ring buffer 水位，偏离目标值时做**极小幅度的重采样补偿**（rubato 可变比率）或偶发丢/插一帧
- 或走平台特定的真 duplex：macOS 用 Aggregate Device，Windows 同一设备走 WASAPI 双向
- **这件事要列入第一周尖刀验证**，不要等发现"唱三分钟后延迟变成 80ms"才处理

### 4.2 🔴 Windows 的延迟天花板

cpal 默认走 **WASAPI 共享模式**，往返约 10~30ms —— 刚好卡在预算边缘，能用但不宽裕。想更低需要：
- **WASAPI 独占模式**：可到 ~5~10ms，但会独占声卡（用户的其他声音全没了），体验取舍
- **ASIO**：cpal 有 `asio` feature，但需要 Steinberg ASIO SDK，**分发有授权限制**，且普通用户电脑上没有 ASIO 驱动（除非装了 ASIO4ALL 或有声卡）

**结论**：Windows 上把 WASAPI 共享模式调到最优（小 buffer + 高优先级线程），实测能不能进 30ms。这是 Windows 平台的 Go/No-Go 点。

### 4.3 🟠 实时线程优先级要自己提

cpal 不会帮你把音频线程提到实时优先级。不做这一步，操作系统调度器会在你不注意的时候抢走 CPU，表现为**偶发爆音**（而且只在用户机器上复现）。

- Windows：`AvSetMmThreadCharacteristics(L"Pro Audio")`
- macOS：`thread_policy_set` + `THREAD_TIME_CONSTRAINT_POLICY`
- Linux：`SCHED_FIFO`（需要 rtkit 或 limits.conf 配置）

用 `audio_thread_priority` crate 可以省事。

### 4.4 🟠 Linux 是三等公民

PipeWire 下还行，PulseAudio 下延迟很差，ALSA 直连最好但设备枚举麻烦。建议：**v1 只发 Windows + macOS**，Linux 社区版按需。

### 4.5 🟡 音高条渲染不要用 React 重渲染

60fps 的音高曲线/波形，走 React state 更新会把主线程打满。用 `<canvas>` + `requestAnimationFrame` + ref 直接绘制，React 只管容器。这是常识但很容易第一版写错。

## 5. 为什么不建议用 Tauri 2 做移动端

Tauri 2 支持 iOS/Android，但对**这个项目**不适用：

- Tauri 移动端**没有低延迟音频能力**。cpal 对 iOS/Android 的支持很弱，你必须自己写 Tauri Plugin，里面是 Swift（AVAudioEngine）和 Kotlin（AAudio/Oboe）原生代码。
- 那意味着：写两套原生音频层 + 一套 Rust DSP + FFI 桥接 + Tauri 插件样板。**比直接写原生 App 工作量还大**，且丢掉了 Tauri 的全部好处。
- Tauri 移动端生态本身仍在成熟中，音频这种边缘场景踩坑无人可问。

**判断：想做移动，就别用 Tauri；用了 Tauri，就先做桌面。**

## 6. 单机形态的新问题：本地推理与分发

这是 v0.2 相对 v0.1 最大的架构变化 —— 换声从「一个 HTTP 请求」变成「把一套神经网络塞进安装包」。

### 6.1 执行后端选择

统一走 **`ort`（ONNX Runtime 的 Rust 绑定）**，按平台切 Execution Provider：

| 平台 | EP | 说明 |
|------|-----|------|
| Windows | **DirectML** ✅ 首选 | 覆盖 N卡/A卡/Intel 核显全部硬件，不挑显卡，这是单机分发最省心的选择 |
| Windows | CUDA | 更快，但只支持 N 卡且运行时包体大。作为**可选加速包** |
| macOS | **CoreML** ✅ | Apple Silicon 上走 GPU/ANE，表现好 |
| 全平台 | CPU 兜底 | **必须有**，但可能是分钟级。低配机默认切轻量模型（DDSP-SVC） |

运行时探测硬件 → 自动选 EP → 在诊断页显示当前用的是哪个，并给出预估耗时。**不要让用户面对一个没有进度的转圈。**

### 6.2 包体：Tauri 的「小」在这里失效

```
Tauri 壳 + React 前端            ~10 ~ 20MB    ← Tauri 的优势区
ONNX Runtime + DirectML 运行时   ~100 ~ 200MB
模型权重（编码器 + f0 + 音色）     ~400MB ~ 1GB+  ← 问题在这
```

**对策：分层下载**

1. **安装包只带壳**（~20MB，秒装）→ 装完立刻可用功能 A（实时耳返），因为 A 是纯 DSP，零模型
2. **首次使用换声时**下载推理运行时 + 基础模型包
3. **每个音色一个独立小包**，选哪个下哪个

这仍然是单机 App：**运行时完全离线，只有一次性下载**。但要接受两个后果：
- 需要一个**静态文件 CDN**（唯一的服务端依赖，运维极轻）
- 完全断网的用户第一次用不了 B → 提供「完整离线安装包」作为官网可选下载

> 顺带一个好处：功能 A 零模型依赖，意味着**安装后 10 秒内用户就能唱上第一句**。这个首次体验比「等 1GB 下载完」强太多，值得作为产品设计的基准点。

### 6.3 推理线程绝不能碰实时线程

已在 §2 的架构图标注，这里重申，因为这是单机形态特有的新风险：

- 推理跑满 CPU/GPU 时，**音频回调会被抢占 → 爆音**
- 即使推理在 GPU 上，驱动层的同步、显存分配也可能造成主机侧卡顿
- **设计上直接规避**：录制会话进行中时，换声任务排队不启动。UI 上串行化，不要给用户「边唱边转」的机会

### 6.4 模型许可证是工程之前的事

本地分发意味着权重文件会随 App 发到用户硬盘上，开源协议的传染性和商用限制会直接落到你身上（so-vits-svc 的 AGPL-3.0、部分上游预训练权重的 CC-BY-NC 等）。

**详见 [可行性分析.md §4](./可行性分析.md) 风险表第一行 —— 这是 🔴 级、且必须在写第一行推理代码之前解决的问题。**

### 6.5 微软系模型资产盘点（许可证友好，重点推荐）

盘点的结论有一个清晰的结构性规律：

> **微软开源了这条流水线的「前半段（理解/编码）」和「运行时」，但没有开源「后半段（歌声生成）」。**

所以微软的东西**能覆盖你约一半的模型需求，而且恰好覆盖在许可证最麻烦的那一半上**。

#### ✅ 可用，且建议直接采纳

| 资产 | 用途 | 许可证 | 价值 |
|------|------|--------|------|
| **WavLM**（Base / Base+ / Large） | **内容编码器**，替代 ContentVec / HuBERT | **MIT** | 🔥 **直接缓解 §6.4 的头号风险**。Base+ 约 95M 参数，比 HuBERT Large 轻得多，适合本地分发。有注意事项见下 |
| **NSNet2**（DNS-Challenge 基线） | 干声**降噪**预处理 | **CC BY 4.0**（署名即可商用） | ✅ 极轻量、官方直接提供 ONNX 权重，**拿来即用**，正好填上可行性文档 §3.4 的预处理环节 |
| **DNSMOS**（DNS-Challenge 内） | 输出音质**客观打分** | 随仓库 | ✅ 可做自动化回归，替代部分人工 MOS 评测（对应可行性文档 §7 指标） |
| **wavlm-base-plus-sv**（说话人验证） | 计算**音色相似度 SIM** | MIT | ✅ 正好是 §7「音色相似度」指标的业界标准算法 |
| **ONNX Runtime + DirectML** | 推理运行时 | MIT | ✅ 已在 §6.1 选定 —— 其实你的运行时本来就是微软的 |

> ⚠️ **WavLM 用于 VC 的关键注意事项**：WavLM 的设计目标之一就是**保留说话人身份信息**（所以它做声纹验证很强）。而音色转换恰恰需要**去掉**源说话人信息。
> 直接拿 WavLM 特征喂解码器会导致**源音色泄漏**（换完还有点像你自己）。
> 对策：取特定中间层而非最后一层、加解耦训练、或走 kNN 检索式转换。**这是要做实验调的，不是配置项。** 建议在第 3~6 周的 B 链路阶段把「WavLM vs ContentVec」做成一组 A/B 实验。

#### ❌ 不可用（容易误判，逐个说明）

| 资产 | 为什么不行 |
|------|-----------|
| **Phi-4-multimodal**（音频） | **只能听不能说** —— 它是 ASR / 语音翻译 / 语音摘要的**理解**模型，没有语音生成能力，做不了 SVC。而且 5.6B 参数对本地分发也不算轻 |
| **VibeVoice**（1.5B / Realtime 0.5B） | 虽然是 MIT 且有轻量版，但它是 **TTS（文字→语音）**，不是 **SVC（人声→人声）**。它不接受你唱的音频作为输入去换音色，用途完全不同。另外：微软曾因深度伪造滥用顾虑**从公开仓库下架过 TTS 代码**，把商业产品架在一个上游被撤下过的模型上，供应链风险要单独评估 |
| **VALL-E / NaturalSpeech 系列** | 研究项目，**无公开可商用权重** |
| **Azure Speech / Custom Neural Voice** | 云服务，与「单机」形态直接冲突；且 CNV 是限制准入的 |

#### 结论

**微软资产能帮你解决：内容编码（WavLM，MIT）、降噪（NSNet2）、质量评测（DNSMOS / WavLM-SV）、推理运行时（ORT + DirectML）。**
**仍然需要从别处拿的：音色解码器 + 声码器（NSF-HiFiGAN / DDSP-SVC / RVC generator 那条线）—— 这部分微软没有开源可用的歌声生成模型。**

许可证审计时，把上表能替换的部分优先替换成微软方案，**剩下要审的范围能缩小一半左右**。

## 7. 横向对比

单机桌面这个前提下的横向对比：

| 方案 | 实时音频 | 本地推理 | UI 开发效率 | 跨平台 | 适配度 |
|------|---------|---------|-----------|--------|--------|
| **Tauri + Rust** | ✅ 优（无 GC，确定性） | ✅ `ort` 成熟 | ✅ 优（React 生态） | ✅ Win/macOS/Linux | ⭐⭐⭐⭐⭐ |
| Electron + Node 原生插件 | 🟠 需 C++ addon，主进程 GC 仍有风险 | 🟠 onnxruntime-node 可用 | ✅ | ✅ | ⭐⭐ 壳本身就 100MB+，单机形态下更亏 |
| JUCE (C++) | ✅ 行业标准，音频最成熟 | 🟠 要自己接 ORT C++ API | ❌ UI 难写 | ✅ | ⭐⭐⭐ 纯音频背景团队可选 |
| Qt / C++ | ✅ | 🟠 | 🟠 | ✅ | ⭐⭐ |
| Flutter | ❌ 低延迟音频生态弱 | 🟠 | ✅ | ✅ | ⭐ |
| Python + PyQt | ❌ GIL，实时音频不可行 | ✅ 最方便 | 🟠 | 🟠 打包噩梦 | ❌ |

**结论：确定单机之后，Tauri 的优势反而放大了。** 因为单机 App 同时需要「硬实时音频」和「本地神经网络推理」两种重负载原生能力 —— 这正好是 Rust 擅长而 JS/Python 做不了的部分，同时 React 又保住了 UI 开发效率。Electron 在这个场景下全面劣势（壳更大、GC 风险、还是得写原生插件）。

**如果想更进一步、连 WebView 也去掉（纯 Rust GUI），见 §10。**

## 10. 纯 Rust GUI 框架选型（去掉 WebView）

### 10.0 先说一个容易搞反的前提

**换 GUI 框架不会让核心风险变好一丁点。**

因为在 Tauri 方案里，实时音频、DSP、ONNX 推理**本来就已经全在 Rust 侧**了，WebView 只负责画界面和收发低频消息。所以：

- ❌ 不要为了「延迟」换纯 Rust GUI —— 热路径已经是 Rust，换了没有收益
- ✅ 该为这些换：**单一语言（不用维护两套工具链）、无 WebView2 运行时依赖、分发更简单、音高条渲染可以直接读原子变量而不过 IPC**

反过来，放弃 WebView 的代价是实打实的：**UI 开发效率下降、设计表现力天花板降低、能招到的人变少**。
这是个「团队构成」决策，不是「技术优劣」决策。

### 10.1 候选框架对比

| 框架 | 范式 | 成熟度 | 自绘能力（音高条） | 消费级颜值 | 许可证 | 结论 |
|------|------|--------|------------------|-----------|--------|------|
| **egui** / eframe | 立即模式 | ✅ 最成熟、生态最大 | ✅ 好（`Painter` / `egui_plot`），立即模式天生适合实时数据 | ❌ 一眼「开发者工具」 | MIT/Apache | ✅ **尖刀 demo + 诊断页首选** |
| **Iced** | 保留模式，Elm 架构 | ✅ 较成熟，System76 COSMIC 桌面在用（重要背书） | ✅ `Canvas` widget 专门干这个 | 🟠 中上，能做但要花功夫 | MIT | ✅ **纯 Rust 做产品的首选** |
| **Slint** | 声明式 DSL + 实时预览 | ✅ 成熟，工具链好 | ✅ | ✅ **最好看** | ⚠️ GPLv3 / 免版税商用 / 付费三选一，**条款有前提** | 🟡 颜值最优，**但商用闭源前必须先核实授权** |
| **Dioxus**（desktop） | React 式 | ✅ | 取决于渲染后端 | ✅（等于 HTML/CSS） | MIT | ⚠️ **桌面端底层仍是 WebView** —— 只统一了语言，没去掉 WebView |
| **Vizia** | 声明式，音频圈出身 | 🟡 | ✅ | 🟠 | MIT | 🟡 audio plugin 场景常见，通用桌面生态小 |
| **GPUI**（Zed 的） | 自研 GPU | ❌ API 不稳、文档稀少 | ✅ 极强 | ✅ 极好 | Apache | ❌ 现在上车太早 |
| **Floem / Makepad / Xilem / Freya** | 各异 | ❌ 早期 | — | — | — | ❌ 不适合做要交付的商业产品 |

### 10.2 推荐

**如果坚持纯 Rust：`Iced` 做产品主 UI + `egui` 做内置诊断页。**

理由：
1. Iced 的 **Elm 架构（Message / update / view）和 React 的心智模型很接近**，从前文的 React 方案切过来不会重写思路
2. Iced 的 `Canvas` widget 正好对应音高条/波形这类自绘需求 —— 而这恰恰是本产品 UI 里**唯一复杂的部分**，其余都是按钮、列表、进度条
3. 本产品的 UI 规模其实很小（导入 / 录制 / 音高条 / 音色选择 / 进度 / 历史 / 诊断，约 6 个界面），**不需要庞大的 widget 库**，Iced 的覆盖面够用
4. MIT 许可，商用无顾虑
5. 诊断页用 egui 单开一个窗口最省事，反正不给普通用户看，丑无所谓

**注意 Iced 的已知代价**：版本间 API 变动较大（升级要做好返工预算）、样式系统不如 CSS 灵活、动画能力弱。做「有呼吸感的消费级界面」会比 React 吃力不少。

### 10.3 真正的决策规则

| 你的情况 | 选 |
|---------|-----|
| 团队有前端能力，想要消费级颜值和快速迭代 | **Tauri + React**（维持 §1~§9 方案） |
| 团队以 Rust / 音频背景为主，接受「专业工具」质感 | **Iced**（+ egui 诊断页） |
| UI 颜值优先，且愿意先花时间核实授权条款 | **Slint** |
| 只是想统一成一种语言，不介意还有 WebView | Tauri + **Dioxus/Leptos** 前端 |

给这个产品的倾向性意见：目标用户是「自认音痴、想开口唱歌」的普通人，**界面的亲和力是产品的一部分**，不是可省的装饰。这一点上 React 仍有明显优势。
除非团队里根本没有前端，否则我**不建议为了纯粹性去掉 WebView**。

### 10.4 一个能让你现在不用做决定的办法

第 1~2 周的尖刀验证反正要写一个**纯 Rust、不带产品 UI 的 demo**（见 §8）。
用 **egui** 给它套个最简界面（延迟读数、xrun 计数、f0 曲线、retune 滑杆）—— 半天工作量。

这个东西不会浪费：
- 它就是将来的**内置音频诊断页**（单机无遥测，这页是刚需，见可行性文档 §5 P0-5）
- 它同时是团队的**开发调试工具**
- 写完之后你对 Rust GUI 的手感有了真实判断，再决定主 UI 用 Iced 还是 React，**决策质量比现在纸上谈兵高得多**

**建议：主 UI 框架的决定推迟到第 3 周，第 1~2 周先用 egui 把尖刀 demo 跑出来。**

## 11. 音频层框架确认（另一种读法）

如果「框架」指的是音频引擎层而非 GUI，结论维持 §3 不变，补充说明：

| 需求 | 选择 | 说明 |
|------|------|------|
| 跨平台音频 I/O | **cpal** | 事实标准。坑在 §4.1（双时钟）和 §4.2（Windows 延迟） |
| 更省心的替代 | `miniaudio` 的 Rust 绑定 | C 库绑定，**自带 duplex 支持**，能绕开 cpal 的双流问题；代价是不够 Rust-native、调试时要看 C 代码。**如果 §4.1 的时钟漂移在尖刀阶段搞不定，这是第一备选** |
| ❌ 不要用 | `rodio` | 只做播放，不是实时处理引擎 |
| ❌ 不要用 | `kira` | 游戏音频，设计目标不同 |
| DSP 组件库 | `fundsp` | 滤波/包络等现成件，但**核心的 YIN + PSOLA 仍需自写** |

### 一个值得记下的「第二形态」

`nih-plug` 是 Rust 的音频插件框架（CLAP / VST3）。如果将来想把这套实时修音引擎**同时发布成 DAW 插件**卖给翻唱/编曲人群，核心 DSP 代码（`audio/pitch.rs` + `psola.rs` + `scale.rs`）是可以直接复用的。

**这意味着一条架构建议**：把 DSP 核心做成一个**不依赖 cpal、不依赖任何 GUI 的独立 crate**（纯函数式：喂 buffer 进去，吐 buffer 出来），App 和未来的插件都只是它的宿主。成本几乎为零，但保留了第二条商业化路径。

> 注意：**优先做 CLAP**（宽松许可），VST3 的 SDK 是 GPLv3 / 商业双授权，闭源发布需要向 Steinberg 申请。
